# The AgentCore temporal policies, checked

The policies from the AWS blog post [*Securing AI agents with temporal policies in Amazon Bedrock
AgentCore*](https://aws.amazon.com/blogs/machine-learning/securing-ai-agents-with-temporal-policies-in-amazon-bedrock-agentcore/)
(Eichenberger, Gordon and Trucksaess, 6 August 2026), checked against **the article's own decision
tables** by Anchor and by the Dogwood engine.

**Scope note before anything else.** These are code listings from a blog post explaining ideas one
at a time, not a deployed policy set. Nothing below is a vulnerability in AgentCore or in Dogwood:
both evaluate these policies exactly as written. The findings are about what the policies, as
published, do — measured against what the same article says they do.

## The source

Every policy here is **the article's listing verbatim**, copied byte for byte from the published page
on 2026-10-02. The page and a PDF of it are recorded in the reference ledger. There is **one edit**:
policy 1 writes its gateway as an unquoted placeholder, `AgentCore::Gateway::<GATEWAY_ARN>`, which
does not parse; it is quoted, `"<GATEWAY_ARN>"`, as policy 7 already writes its own placeholder.

**Policy 6 is not here.** As published it does not parse, in Dogwood, not only in Anchor. Its
predicate lacks the `::<kind>` segment and its fields their `input.` group
(`AgentCore::Action::"execute_buy"{ stock_symbol: … }`), and the listing has one closing brace too
many. Repairing a published policy and then reporting on it would be reporting on our repair.

## The article's own tables, as ground truth

For six of its seven policies the article prints a table of **Expected result**s: a trajectory, an
action, ALLOW or DENY. Those are AWS's own statement of what each policy is for, and they need no
interpretation of ours. [`tables/`](tables) holds each one, in the conformance format of
[`tests/policies/agentcore/`](../../tests/policies/agentcore/README.md): the published policy verbatim,
and each table row as a session with its expected decision.

Where the published policy does **the opposite** of what its table says, the row is marked `finding`.
That makes each finding a checked fact rather than a reading: both Anchor's model and the Dogwood
engine are held to it, and a finding that ever stopped reproducing would turn the run red.

```bash
python tests/strands/agentcore_replay.py --suite examples/aws1/tables       # the Dogwood engine
python tests/strands/agentcore_conformance.py --suite examples/aws1/tables  # Anchor's model
```

**131 decisions, all reproduced by both, 16 of them findings.** The engine reads the article's
policies as published, under AgentCore's event schema. It needs an action schema for the article's
tools, which the article does not give. [`tables/blog.cedarschema`](tables/blog.cedarschema) is ours,
and states its two assumptions: `execute_trade`'s inputs are required, and `get_client_profile`
returns a `portfolio_id`.

## What was found

### 1. Deployed together, the policies allow a trade from an empty trajectory

**The headline, and the reason the rest matter.** Cedar permits by positive match: in a set, any one
`permit` that matches grants. The article publishes four `permit`s on `execute_trade`, and two of them
match a trajectory in which nothing has happened:

- **Policy 4, the budget cap**, is a `permit` whose condition is that the quotes so far total under
  $60,000. With no quotes the total is 0.
- **Policy 7, trust decay**, is a `permit` that holds whenever no advisor has interacted in the last
  15 minutes (finding 2).

So a $30,000 trade attempted first thing in a session — no profile looked up, no price, no
approval — **is allowed**. The engine says so, and names policies 4 and 7 as the rules that decided
it. In [`tables/00-published-set.dw`](tables/00-published-set.dw), every DENY row the article prints
for a trade is allowed by the published set:

| the article's table says DENY | the set as published |
|---|---|
| policy 3: price never called | ALLOW |
| policy 3: price 2 minutes ago | ALLOW |
| policy 5: $30,000, no approval | ALLOW |
| policy 5: a second $30,000, the approval already consumed | ALLOW |
| policy 2: lookup returned port-8821, trade names port-3347 | ALLOW |
| policy 4: $37,000 traded, $30,000 more | ALLOW |
| policy 7: 20 minutes since the advisor | ALLOW |

```bash
python src/checker/properties.py examples/aws1/agent-policy.dw --property examples/aws1/EmptyTrajectory.tla --witness
```

### 2. Policy 7 is inverted

> "After 15 minutes without advisor interaction, the agent loses access to write operations."

The policy is `permit … unless temporal { formerly within 15m …interact_advisor::response{…} }`.
`unless` blocks a rule when its body holds, so this permits a write while the advisor has **not**
interacted in the last 15 minutes, and refuses one while they have. The article's own table for it
fails on both of its write rows:

| the article's table | the policy |
|---|---|
| 3 minutes since the advisor, execute_trade: **ALLOW** | DENY |
| 20 minutes since the advisor, execute_trade: **DENY** | ALLOW |

It covers `rebalance_portfolio` too, the other write operation the prose names, with the same
inversion. `TrustDecay.tla` states the sentence as claims, and all of them break.

### 3. Policy 2 checks what was asked for, not what was returned

> "The portfolio_id passed to execute_trade must exactly match one of the portfolio IDs returned by
> get_client_profile."

The policy compares the trade's `input.profile_id` with an earlier `get_client_profile`'s
`input.profile_id`: a **profile** id, and the one the lookup was **asked** for. It never reads a
portfolio id, and never reads anything the lookup returned. AWS's own guide draws exactly this line:
"an input correlation matches what the earlier call requested; an output correlation matches what it
returned" (*Temporal policy examples*, AgentCore Developer Guide). So the table's DENY row — lookup
returned port-8821, trade names port-3347 — is allowed when the trade names the same client.

How much this matters depends on the tool. A lookup for an id that does not exist presumably fails,
recording an `error` and not the `response` the policy needs. It is reported as a mismatch with the
article's description, not as an exploit.

### 4. Policy 4 caps quotes, not trades

> "Total trade value in a single policy session (or trajectory) cannot exceed $60,000."

The policy sums the `cost` of `get_market_price` **requests**. Its table counts trades: $15,000,
then $22,000, then $30,000 denied at $67,000. With those trades made and no quotes, the policy allows
the third. It does deny it if each trade was first quoted at its own cost, which is the one reading
under which it caps anything. Both rows are in [`tables/04-cumulative-budget-cap.dw`](tables/04-cumulative-budget-cap.dw).

### 5. Two names for one action

Policy 1 names its actions `FinTarget___load_portfolio` and `FinTarget___rebalance_portfolio`; every
other policy, and policy 1's own table, names them bare. In the set these are different actions. The
chain policy 1 enforces — no rebalance without a profile then a portfolio load — applies to
`FinTarget___rebalance_portfolio`, while policy 7 grants `rebalance_portfolio` from an empty
trajectory. AgentCore names an MCP tool's action `<Target>___<tool>`, so on a real gateway the bare
names would match nothing; whichever spelling is meant, it has to be one.

### 6. One approval, two trades

> "Each approval covers exactly one execution."

Policy 5 consumes an approval when a trade's `response` is recorded. AgentCore records a response
"shortly after" the call completes, so a second trade sent before the first one's response lands
finds the approval unconsumed, and both are allowed. This is not a defect in the policy: no policy
can close it, and the guide's own advice is to wait for each response before the next request. It is
a limit on what "one approval per trade" means for an agent that does not wait. It stays a finding in
the fixed set too.

### Smaller things

- **The threshold is off by one.** The prose requires approval for a trade "exceeding $25,000"; the
  policy's `cost < 25000` sends a trade of exactly $25,000 to the approval branch. A row in the tables.
- **Policy 6 does not parse**, above.
- **"Your first 100 temporal policies per policy engine"**, in the article's cost section; the
  AgentCore guide's quota table allows 20 per engine.

## The fix

[`fixed/agent-policy.dw`](fixed/README.md) is the whole set corrected, in AgentCore's own form. It has
one `permit` for what every trade needs (integrity on what was returned, freshness), and `forbid`s for
what takes access away (budget over trades, approval over $25,000, trust decay the right way round).
It satisfies every row of every table — 68 decisions, checked by Anchor and confirmed by the engine —
with finding 6 the only one left.

## Everything above, from one command

```bash
anchor check examples/aws1 --full --no-llm --smoke --attempts 4
```

The reports here were generated with exactly that. **`--smoke` because the set is too big to
exhaust**: the full set has twelve rules, and an exhaustive rule-by-rule run did not finish in many
minutes. `--attempts 4` because the fixed set's trust-decay `forbid` means an allowed trade needs four
requests (advisor, profile, quote, trade). A random walk reports `live` or `unknown`, never VACUOUS,
so the rule-by-rule half says little here. The property modules are exhaustive whatever the flags,
and the tables are the real check.

Finds the policy sets and the property modules by globbing, runs every check, and writes
[`findings.md`](findings.md), `findings.html`, `results.json` and `traces/`. Without `--no-llm` it also
puts the questions in [`questions.md`](questions.md) to an agent, which calls a model. It exits **1**
when there is something to look at, so it can gate a pipeline, and **3** when the run could not happen
at all. The tables are checked by the two harnesses above.


## What this example is evidence for

Three kinds of question:

1. **Does it parse and type-check?** `dogwood validate`. Five of the seven policies do as published,
   and policy 1 does with its placeholder quoted.
2. **Is any rule inert?** The derived questions: every rule in the set is live. True, and no comfort:
   a rule that grants too much is live.
3. **Does it do what its author said?** Only an author can state that, and here the author did — in
   the tables. Checked against them, the set denies none of the trades its tables deny.

The survey literature calls the gap between (2) and (3) the *user-intent formalization gap*. What this
example adds is that the intent was already written down, as decision tables beside the policies, and
nothing checked one against the other. Checked mechanically, every disagreement comes with a session
the engine confirms.
